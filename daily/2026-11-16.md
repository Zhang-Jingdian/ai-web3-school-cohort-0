## 学习笔记（脚手架，请补自己的理解）

### 为什么要学这个
- AI 应用最大的问题之一是输出质量不稳定：改了一句 prompt，某些问题变好了、另一些变差了；换了模型，平均效果提升但关键场景出错；接了 RAG，答案更长但引用反而不准。
- Evaluation 要解决的就是这些：用明确样本、指标、评分方式和回归测试，判断系统是不是真的变好了。
- 学 eval 的目标不是做一份漂亮报告，而是让团队能回答：**这次改动有没有让关键任务更可靠？有没有引入新的失败模式？**

### 第一性原理
- **不能被重复测量的 AI 行为，就不能被稳定改进。** AI 输出有概率性、用户问题又开放，没有固定样本和评估标准，就很难知道变化来自真实改进、运气、还是样本太少。
- 三条硬规则：
  - **先测任务，不只测模型**：用户关心的是整条链路是否完成任务，不是模型榜单分数。
  - **先保住关键失败场景**：高风险错误、常见问题、边界条件，要进 regression set。
  - **评估要贴近产品**：离真实输入越远，eval 越容易变成自我安慰。

### 知识节点
- **Harness**：运行 eval 的框架，负责喂样本、调用系统、收集输出、运行 grader、记录结果。一个最小 harness 至少要有：输入样本、期望输出或评分规则、被测系统版本、模型和参数配置、运行日志、结果报告。Harness 的价值是**可重复**——没有可重复运行的 eval，就很难比较不同 prompt、模型、检索策略。
- **Golden Set**：一组认真挑选和标注的测试样本，不一定要大，早期 30–100 条高质量样本往往比一堆随便收集的问题有用，关键是覆盖真实任务和关键失败模式。应包含：常见正常问题、边界问题、易误判问题、高风险问题、历史 bug、用户真实反馈。**每修一个重要 bug，都应该考虑把它变成 regression 样本。**
- **LLM-as-Judge**：用模型给模型输出评分，适合开放式答案（摘要质量、是否完整、是否遵循格式、是否引用来源）。但**不能被神化**——judge 也会偏、会漏、会被输出风格影响。更稳的做法：可自动判断的字段用规则评分、开放式质量用 LLM judge、高风险样本保留人工抽检、定期校准 judge 和人工评分的一致性。**LLM-as-Judge 是评估工具，不是最终真相。**
- **Regression**：防止旧问题复发。AI 应用很容易「修 A 坏 B」，一次 prompt 修改、模型升级、retriever 调整都可能影响很多旧场景。实用做法：用户反馈错误 → 复现并记录输入 → 标注期望输出或拒答条件 → 加入 regression set → 每次发布前跑一次。
- **Observability**：线上观察系统行为的能力。Eval 多发生在发布前，observability 发生在真实使用中。至少要记录：输入类型和来源、检索结果、工具调用、模型输出、错误和重试、用户反馈、成本和延迟。**没有 observability，就不知道真实用户在哪里失败，也不知道该往 golden set 里补什么。**

### 在 AI x Web3 中的位置
AI x Web3 系统里 eval 更重要，因为错误可能影响资产、权限、治理判断和链上执行。需要特别评估：交易解释是否准确、风险提示是否漏报、工具调用参数是否越界、是否能拒绝不确定请求、是否能识别 Prompt Injection、引用和来源是否可追溯、高风险动作是否要求 human check。**Eval 不会替代交易模拟和权限控制，但它能让你持续发现系统在什么场景下不可靠。**

### 最小实践
给「交易解释 / 文档问答 / Agent 工具调用」原型做最小 eval。准备 30 条样本（10 正常 / 10 边界 / 5 历史 bug / 5 恶意注入），每条定义：输入、期望行为、必须包含的信息、必须拒绝或提醒的情况、是否需要引用来源。每次改 prompt、模型或检索策略前后跑一遍，记录变化。

## 我的理解 / 疑问

**我的理解**（你的话，Learning Agent 润色）：

1. **eval 把「主观感觉」变成「可重复测量」**：AI 输出有概率性、用户问题又开放，没有固定样本和评估标准，就分不清变化是真实改进、运气还是样本太少。所以顺序是「先测任务、不只测模型」——用户关心整条链路有没有完成任务，不是模型榜单分数。
2. **Golden Set 不追求大，追求覆盖关键失败模式**：30–100 条高质量样本比一堆随便收集的问题有用，关键是把正常 / 边界 / 易误判 / 高风险 / 历史 bug / 真实反馈都盖住。「每修一个重要 bug 就把它变成 regression 样本」这条我最有共鸣——它把「踩过的坑」固化成永久的回归护栏。
3. **LLM-as-Judge 是评估工具，不是最终真相**：judge 也会偏、会漏、会被风格影响，所以能自动判断的用规则、开放式的才用 judge、高风险的留人工，还要定期校准。在 Web3 场景这条更重——错误可能影响资产、权限、治理判断和链上执行，eval 不能替代交易模拟和权限控制，但能持续暴露「系统在什么场景下不可靠」。
