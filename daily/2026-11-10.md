## 学习笔记（脚手架，请补自己的理解）

### 为什么要学
- LLM 不会自动连接你的数据库、文件系统、API、用户历史或项目文档，它只基于当前上下文生成输出；上下文错了、缺了、过期了，模型再强也给不可靠答案。
- 很多 AI 应用问题表面看是「模型不够聪明」，实际是 context 设计混乱：把不可信网页当系统指令、把旧文档当最新规则、把用户愿望当事实、把上次任务的状态泄漏到下次任务。
- 带工具调用的场景里这直接关系安全：模型看不到真实工具结果就只能猜；Agent 不知道当前状态、权限和预算，就可能生成越界操作。

### 第一性原理
- **模型只能基于它看见的上下文行动；系统必须决定什么能进上下文、带着什么身份进去、过期后怎么退出。**
- Context 不是长文本拼接，而是一套信息治理问题：为每类信息标注来源、时效、权限、可信度。
- 三条硬规则：
  - **可信来源要显式标注**：系统状态 / 用户输入 / 检索文档 / 工具结果要分区放置。
  - **上下文要可刷新**：状态、配置、权限、价格、版本、任务进度不能长期缓存后继续用。
  - **记忆要可撤销**：用户偏好和历史任务可以提升体验，但不能变成隐藏权限或永久身份假设。

### 知识节点
- **Context Window**：模型一次请求能处理的最大上下文范围。窗口大 ≠ 用好，长上下文常见问题是「看见了但没抓住重点」。实际产品里应配合检索、摘要、结构化数据使用：关键状态直接给，长文档按需取，低可信内容隔离标注。
- **Context Engineering**：设计上下文「进入模型的方式」——选择数据源、排序、裁剪、标注来源、隔离不可信内容、决定哪些信息必须每次重新查询。稳定的工具型 Agent 上下文不只「用户问题 + 一段 JSON」，还应含：当前任务状态 / 工具返回结果 / 相关日志或证据 / 可信数据来源 / 外部检查结果 / 用户原始意图 / 系统禁止事项和输出 schema。目标不是塞满窗口，而是让模型在正确的信息层级里工作。
- **Memory**：跨请求保留的信息（用户偏好、历史任务、常用钱包、项目配置、上次分析结果）。便利但带隐性风险：记住「用户常用 0xabc 地址」就默认它当收款地址，记住「用户风险偏好较高」就放松高风险确认。**Memory 不能替代实时授权**，所有涉及身份、权限、资产、外部副作用的记忆都必须重新绑定当前会话和当前授权。
- **Knowledge Base**：可检索的外部知识库（产品文档、SDK 文档、FAQ、runbook）。解决模型知识过期，但不自动保证正确；至少要记录：文档来源和 URL / 最后更新时间 / 适用协议版本 / 适用运行环境 / 官方还是第三方 / 是否需人工复核。否则 RAG 只会把旧错误更稳定地送进模型。

### 在 AI x Web3 中的位置
Context 是连接模型和现实系统的入口：AI 负责推理，Web3 负责状态和结算，context 决定模型看到的是「用户幻想 / 过期文档 / 可验证的链上事实」。靠谱的 Agent 上下文分五层：
1. **指令层**：系统规则、工具使用规则、禁止事项
2. **任务层**：用户目标、本次会话参数
3. **事实层**：链上状态、工具结果、simulation
4. **知识层**：文档、标准、论坛、历史案例
5. **记忆层**：用户偏好和项目配置

层级越清楚，后续越容易做权限控制、prompt injection 防护和审计。

## 我的理解 / 疑问

**我的理解**（你的话，Learning Agent 润色）：

1. **Context 不只是「模型能看见的信息」这么简单**——它要分区管理不同来源（系统规则、外部文档、用户输入、工具结果），让每类信息带着自己的身份和可信度进来，这正是「信息治理」的意思。
2. **记忆层（Memory）最让我印象深刻**：它存的是 context，用来提供会话之外的信息；但如果不当心，它会变成一种「隐性约束/默认」——比如记住常用地址就默认它是收款地址。所以记忆不能替代实时授权。
3. **Memory 和外部文档都不能被当成事实**——因为它们可能过期、没经过本次会话的核实，而且模型本身会幻觉（hallucination）。它们只能是「候选信息」，关键事实还得来自实时查询的可信来源。
