## 学习笔记（脚手架，请补自己的理解）

### 为什么要学
- LLM 训练知识会过期，context window 也放不下整个互联网、全部协议文档和历史治理讨论。RAG 的作用：用户提问时，系统先从知识库找相关材料，再让模型基于这些材料回答。
- RAG 很常见：产品文档问答、代码库助手、研究摘要、客服知识库、SDK Copilot、内部知识检索。但很多 Demo 只做到「能搜到一些段落」，没做到「答案能被验证」。
- **RAG 的核心不是让回答更长，而是让回答有来源、有版本、有边界**。没有 citation 和 freshness 的 RAG，只是把幻觉从模型内部搬到检索系统里。

### 第一性原理
- **RAG 的可靠性取决于证据链，不取决于向量库这个名词。** 一个 RAG 系统至少有三次判断：文档怎么切、查询时取哪些内容、生成时如何引用和拒答。任何一层做错，模型都会拿着错误材料说得很顺。
- 三条硬规则：
  - **检索结果不是事实**：它只是候选证据，仍要看来源、时间、版本、适用范围。
  - **引用要能回到原文**：答案里的关键判断应能追溯到具体文档、段落或链上记录。
  - **检索失败要允许拒答**：找不到证据时说「不确定」，而不是让模型补全。

### 知识节点
- **Chunking**：把长文档切成可检索片段。切太小语义断裂；切太大噪声多、token 成本高。技术文档要按结构切（标题 / API endpoint / 函数说明 / 参数表 / 风险提示 / FAQ / 审计记录），每个 chunk 保留来源 URL、标题路径、更新时间和版本。
- **Vector DB**：存 embedding 并按相似度检索相关 chunk。但**向量相似 ≠ 答案正确**（旧版本 SDK 文档可能高度相似却已不适用）。所以向量库里还要存 metadata：来源、版本、chain、更新时间、可信等级、是否废弃；检索时**先过滤，再排序**。
- **Retriever**：根据用户问题取回候选材料的组件（向量 / 关键词 / 混合 / 图检索 + metadata filter）。不能只看语义相似度，还要知道用户问的是哪个产品、哪个版本、哪段时间、官方还是社区。判断句：**如果问题里有版本、环境、时间、地址或具体对象，retriever 就不该只做纯向量搜索。**
- **Rerank**：初步检索后对候选重排，把更相关、更可信、更完整的排前面。减少「标题相似但内容不对」的结果；增加延迟和成本，按场景决定要不要加。
- **Citation**：把答案里的关键结论连回来源，是用户验证答案的入口，不是装饰。至少要说明：来自哪份文档/链上记录、来源是否官方、版本/更新时间、哪些结论只是模型归纳、哪些地方没足够证据。

### 在 AI x Web3 中的位置
RAG 位在 Knowledge Base 和模型之间：帮 Agent 查资料、补上下文、引用证据，但不负责最终执行。常见应用：协议文档问答、合约接口解释、治理提案/论坛摘要、审计报告检索、SDK/API Copilot、交易解释补项目背景。**当 RAG 结果要影响链上动作时，还要接 simulation、policy、human check**——文档说某函数「可以调用」，不等于当前用户「应该签名」。

### 最小实践
做「协议文档 RAG 问答」最小版（见「推荐路径」）。重点：证据链，不是 UI。输出强制区分 `answer` / `sources` / `uncertainties` / `needs_version_check`。

## 我的理解 / 疑问

**我的理解**（你的话，Learning Agent 润色）：

1. **可靠性靠证据链，不靠向量库**：向量库只是个「存 + 查」的工具，里面可能存着过期信息；而模型本身会幻觉、产出无来源的回答。所以光有向量库没用，必须靠「来源、版本、时效、引用」这条证据链兜底。
2. **Citation 最能防「把幻觉搬进检索系统」**：它把答案连回具体来源，逼着回答有据可查。没有 citation，前面检索得再好，也没法判断答案是「有证据」还是「模型自己编的」。
3. **向量相似 ≠ 答案正确**（Learning Agent 补的示例）：比如用户问「这个合约的 withdraw 怎么调」，检索可能按语义相似返回一个「同名但不同协议」的合约文档，答案看起来对、其实是错的；旧版本文档也可能和当前问题高度相似但已不适用。所以检索要「先按来源/版本过滤，再按相似度排序」。
