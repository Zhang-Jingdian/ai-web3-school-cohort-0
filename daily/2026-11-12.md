## 学习笔记（脚手架，请补自己的理解）

### 为什么要学这个
- LLM 一次回答通常只是生成文本；Agent 更进一步：拆任务、查资料、调用 API、写代码、生成操作草稿、等反馈再继续。
- 真正的风险点：一旦 Agent 能调用工具、写入系统、提交请求或触发支付，错误就不再是「答错」而是「做错」。
- 所以 Agent 的核心不是让模型更像人，而是让**执行循环有清楚边界**。分工是：模型提候选行动，系统限制行动空间，用户批准高风险边界。

### 第一性原理
- **Agent 不是自主权本身，而是被约束的执行循环。** 目标、工具、状态、权限和停止条件缺一不可。
- 只有模型 + 工具的 Agent 只是「会说话的脚本执行器」。真正可用的 Agent 必须知道：能做什么、不能做什么、做完如何验证、失败如何停止、谁能审计它做过的事。
- 三条硬规则：
  - **工具比回答更危险**：读数据、写数据库、发请求、改配置不是同一风险等级。
  - **状态必须外置和可查**：任务进度、工具结果、失败原因、用户确认都要记录，不能只藏在模型上下文里。
  - **停止条件要明确**：达到目标、超出预算、信息不足、风险越界、用户拒绝，都应让 Agent 停下来。

### 知识节点
- **Tool Use**：Agent 调用外部能力（搜索、数据库、API、代码执行、支付接口等），让它从「会回答」变成「能做事」。但工具也放大了 Prompt Injection 和模型误判的危险——能读网页的 Agent 被恶意网页影响 vs 能写系统的 Agent 被影响，后果完全不同。工具设计要明确：输入 schema、权限范围、是否只读、是否产生外部副作用、调用前后如何记录、哪些调用需人工确认。
- **Planning**：把目标拆成步骤（如「分析这个 DAO 提案」→ 读提案、检索历史、总结争议、查投票机制、出风险清单）。计划只是候选路线，不是授权；越靠近高风险动作越要拆开检查。好计划应暴露：每步用什么工具、读还是写、哪些可自动执行、哪些需确认、失败可否重试、如何验证完成。
- **State**：Agent 当前任务状态（目标、已完成步骤、工具返回、错误、预算、确认记录、最终输出）。只放 prompt 历史不够，生产系统需要可查询、可恢复、可审计的 state，否则很难回答「Agent 为什么调了这个工具？是否拿到确认？哪一步开始偏离目标？」。有外部执行时还要记环境、版本、关键参数、确认请求和撤销事件。
- **Reflection**：让 Agent 检查自己的中间结果（信息不足、工具失败、计划不合理）再修正。适合提质量，但**不能替代外部验证**——自我反思仍由模型完成，模型可能给自己的错误找理由。写入、授权、支付这类动作，reflection 只能辅助诊断，不能作最终安全判断。
- **Multi-Agent**：多个 Agent 分工（研究读资料、开发写代码、安全做审查、执行调工具）。适合复杂工作流，但会放大协调问题：上下文传递丢失、责任边界模糊、一个 Agent 的错误被另一个当成事实、工具权限扩散。做之前先问：多个 Agent 是否真的减少复杂度？把不清楚的流程拆成多个不清楚的角色，只会更难调试。

### 在 AI x Web3 中的位置
Agent 位在模型能力和链上执行之间：能把用户目标推进成多步流程，但不能绕过账户、权限和结算规则。一个相对稳的 AI x Web3 Agent 架构通常是：用户提目标约束 → Agent 读上下文出计划 → 系统把计划拆成只读步骤与候选写入步骤 → 只读工具自动执行、写入工具进 policy 检查 → Simulation 展示链上影响 → 用户确认高风险动作 → Wallet / Smart Account 执行 → 日志记录每一步与最终状态。**最危险的设计：让 Agent 同时拥有模糊目标、广泛工具、长期记忆和大额资产权限。**

### 最小实践
做「DAO 提案研究 Agent」最小版：只执行只读动作，不直接投票；输出里明确来源、证据不足、治理/资金风险、投票前还需人工检查什么。完成后设计权限升级版——只有用户明确授权 + 投票交易 simulation 后，才允许生成投票交易草稿。

## 我的理解 / 疑问

**我的理解**（你的话，Learning Agent 润色）：

1. **Agent 本质是个「会执行、权限还很大」的工具**：它的核心不是更像人，而是「在受规范约束的行为下干活」。学 Agent 的重点就是把行为边界和权限规范建起来，让这个权限大的工具只做被允许的事。
2. **回答只是「说」，工具就要「真的干起来」**：LLM 说错最多误导人，Agent 一旦调工具去写库、发请求、触发支付，就是「做错」——说错和做错是两个完全不同等级的风险。
3. **state 是个保险，防止出问题后无从溯源**：把目标、工具调用结果、确认记录都落到可查的 state，出事时才答得上「为什么这么干、谁批准的、哪一步开始偏了」；如果只存在 prompt 历史里，这个保险就失效了。
