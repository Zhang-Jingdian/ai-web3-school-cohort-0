## 学习笔记（脚手架，请补自己的理解）

### 为什么要学这个
- AI 应用真正进入工作流后，模型不可能只靠 prompt 里的文本完成任务。它需要读文件、查数据库、访问文档、调用 API、操作工具、拿到用户上下文。
- 如果每个应用都用自己的方式接工具，Agent 生态会非常碎：同一个工具要为不同客户端写很多适配层，权限、schema、错误处理和日志也难统一。
- MCP 的价值在于把这层连接抽象成协议——可以把它理解成 AI 应用的「工具接口标准」：客户端负责和模型交互，server 负责暴露资源、工具和 prompts。

### 第一性原理
- **模型不应该直接拥有世界；它应该通过明确协议访问被授权的上下文和工具。**
- MCP 的关键不是「能接更多工具」，而是让工具接入变得**可描述、可发现、可限制**。一个 server 暴露了什么能力、输入 schema 是什么、返回什么结果、哪些动作有副作用，都应该被清楚表达。
- 三条硬规则：
  - **工具要有 schema**：没有 schema，模型调用工具就会变成自然语言猜参数。
  - **权限要在协议外也成立**：协议能描述能力，但真正的授权、审计和隔离仍要由系统实现。
  - **错误要可传递**：工具失败、超时、权限不足，必须明确返回，而不是让模型猜。

### 知识节点
- **Server**：MCP Server 是提供能力的一侧，可以暴露 resources、tools、prompts，让 AI 客户端读取信息或调用动作。设计重点是边界：暴露哪些资源、哪些工具只读/有副作用、参数 schema 是否清楚、错误如何返回、是否需要用户授权、日志和审计在哪记录。一个不加限制的 MCP server，很容易把本地文件、内部 API 或高风险动作暴露给模型。
- **Client**：MCP Client 是连接模型和 MCP server 的一侧（桌面应用、IDE、Agent runtime、聊天客户端）。它负责发现 server 能力、把工具信息交给模型、把模型生成的调用请求转回协议消息，还应负责用户确认、权限提示、会话隔离和工具调用展示。判断 client 是否靠谱，重点看它是否让用户知道：当前连了哪些 server、模型能调哪些工具、调用前是否需要确认。
- **Tool Schema**：描述工具名字、用途、参数、返回值和约束，是模型正确调用工具的关键。好的 schema 不只是字段类型，还要说明：什么时候用、参数代表什么、哪些必填、是否修改外部状态、失败时返回什么。Tool schema 写得模糊，模型就会用错误参数填空。
- **Permission**：MCP 真正进入产品时最容易被低估的问题。让工具连接更方便，但方便不等于安全——读文档、查 issue、建 PR、发支付、删文件风险完全不同。至少要区分：只读还是写入、当前会话授权还是长期授权、是否需要用户确认、是否访问敏感信息、是否产生外部副作用、是否可撤销和审计。**server 暴露能力之前，应该先定义权限模型。**

### 在 AI x Web3 中的位置
MCP 在 AI x Web3 中可以作为 Agent 连接链上工具和开发工具的接口层：读区块浏览器、查合约文档、调 RPC、生成交易草稿、读项目 issue。但 **MCP 本身不是钱包安全方案**——它可以标准化工具入口，不能替代账户权限、交易模拟、签名确认、session key 和审计日志。比较稳的设计：**MCP 负责工具发现和调用格式；Web3 账户系统负责最终权限和执行边界。**

### 最小实践
做一个只读 MCP server，只暴露两个工具：`search_docs(query)` 搜索本地项目文档、`get_file(path)` 读取白名单目录里的文件。要求：不能读白名单外路径、返回结果带来源路径、工具调用写日志、错误明确返回而非静默失败。完成后，再设计一个「写入工具」的权限升级方案：什么时候要用户确认、如何撤销授权、如何审计每次调用。

## 我的理解 / 疑问

**我的理解**（你的话，Learning Agent 润色）：

1. **MCP 是「工具接口标准」，不是「让模型变聪明」**：它不碰模型的智力，只解决「模型怎么用外部能力」这件事的工程化——接入要可描述（schema）、可发现（list_tools）、可限制（权限）。所以判断一个 MCP 实现好不好，看的不是「接了多少工具」，而是「接入之后是不是可控的」。
2. **方便不等于安全，Permission 是这条最容易踩的坑**：MCP 让工具连接变方便，但「方便」会放大风险——读文档、查 issue、发支付、删文件，风险完全不同。这条和 Vibe Coding 里「AI 帮你写代码，但不能替你承担工程判断」是同一件事：**协议能描述能力，不能替你承担安全责任，权限必须在协议之外由系统实现。**
3. **它把前面几章串起来了**：Tool Schema 本质就是 prompt 的一部分（呼应 Prompt 章节）；Agent 的工具调用要和状态、权限、停止条件一起设计（呼应 Agent 章节）；MCP 把「工具」从各 app 私有实现变成标准协议，正好落在 Frameworks / Vibe Coding 讲的「边界」上。今天做的只读 server，本质就是把「边界」落成代码。
