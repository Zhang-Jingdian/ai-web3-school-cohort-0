## 学习笔记（脚手架，请补自己的理解）

### 为什么要学这个
- AI Coding Agent 已经能读代码、改文件、跑测试、解释错误、生成 PR，明显改变开发速度。但速度变快之后，真正的问题变成：你能不能清楚描述任务、能不能审查结果、能不能控制改动范围、能不能验证没有引入新 bug。
- Vibe Coding 最容易被误解成「凭感觉写代码」。实际可用的做法正好相反：**要更清楚地管理 repo、任务、上下文、测试和提交边界**。
- AI 能帮你写更多代码，但不能替你承担工程判断。

### 第一性原理
- **AI Coding 的核心不是自动生成代码，而是把工程反馈循环压短。** 过去要自己搜索文件、理解模块、改代码、跑测试、看错误、再修改；现在 Agent 可以并行承担很多步骤。但如果反馈循环里没有测试、审查和版本控制，速度只会放大混乱。
- 三条硬规则：
  - **任务要小**：越具体、越有边界，Agent 越容易产出可审查结果。
  - **上下文要准**：让 Agent 看对文件、设计约束和错误输出，比写长篇需求更重要。
  - **验证要硬**：运行测试、类型检查、构建、截图或日志，比「看起来对」可靠。

### 知识节点
- **Vibe Coding（初级）**：先理解人和 AI Coding Agent 怎么分工——**人负责目标、边界和验收，Agent 负责搜索、生成、修改和执行**。适合：搭原型、修小 bug、补测试、写脚本、重构局部模块、解释陌生代码。不适合：无边界地「重写整个项目」。
- **Claude Code / Codex CLI（初级）**：把 AI Agent 放进本地开发环境，让它读文件、编辑文件、运行命令、理解测试输出。关键价值不是「聊天」，而是**能在 repo 里行动**；也正因为它能行动，你要明确：哪些文件可改、哪些命令可跑、是否允许装依赖、是否允许访问网络、什么时候必须停下来让人确认。
- **Model / API Config（中级）**：处理模型选择、API key、工具权限、上下文、成本和日志。常见坑：本地和 CI 模型不一致、API key 泄漏到日志/提交、上下文太长导致成本失控、Agent 用了不合适工具权限、输出风格和项目规范不一致。好的配置应能被团队复用，而不是每个人在本机随手调。
- **GitHub / gh（中级）**：把 AI 生成的改动放回版本控制、issue、PR、review 流程。Agent 可以帮看 issue、生成 branch、读 PR diff、写提交信息、整理 review，但**版本控制仍是人类审查的关键线**。原则：让 Agent 多做局部 patch，少做不可追踪的大改动；每次改动后至少看 `git diff`、修改文件列表、测试结果、有没有不该提交的密钥/日志/构建产物。
- **CLI / Script（中级）**：把 Agent 输出变成真实命令和脚本，关注读写范围、dry run 和外部副作用。两个边界：读写文件前确认范围；会修改外部状态的脚本先 dry run。删文件、发请求、改数据库、提交交易、调生产 API，不能只靠 Agent 判断。
- **Repo Workflow（高级）**：把 AI Coding 接进 issue → branch → commit → test → review → merge → release，判断什么时候让 Agent 继续、什么时候必须人停下来审查。不要让 AI 绕过流程，而是让它参与：从 issue 提炼任务边界、搜索相关文件、生成最小 patch、跑测试解释失败、补 changelog/文档、写 PR summary。

### 在 AI x Web3 中的位置
AI x Web3 项目通常同时有前端、合约、脚本、索引器、Agent 后端和文档，Vibe Coding 能显著加快探索速度，尤其适合 hackathon 和早期原型。但**链上相关代码风险更高**：合约、签名、权限、支付、迁移脚本不能只靠 Agent 生成后直接上线。AI Coding 可以帮你写测试、解释 ABI、生成脚本，但高风险动作必须经过审查、模拟和多方确认。

### 最小实践
选一个小功能，让 AI Coding Agent 完成一轮完整工程闭环：写清任务边界和不能改的文件 → Agent 搜索相关代码给计划 → 做最小 patch → 跑测试/构建 → 人看 `git diff` 审查 → Agent 写 PR summary 和验证说明。完成后记录：哪些信息给少了、哪些测试缺失、哪些改动需要人类判断。

## 我的理解 / 疑问

**我的理解**（你的话，Learning Agent 润色）：

1. **AI 帮你写更多代码，但不能替你承担工程判断**：正因为 Agent 把「写」的速度提上来了，工程判断反而更重地压回到我身上——我得把 repo、任务、上下文、测试、提交这些边界写得更清楚。所以 Vibe Coding 不是「凭感觉写代码」，而是「更明确地表达我要什么、接受什么」。
2. **「看起来对」没法在反馈循环里验证可靠性**：代码能不能跑、有没有引入新 bug，只有测试/类型检查/构建/日志能证明；「看起来对」只是主观印象，进不了可重复的验证循环。所以验证要硬，不能靠感觉验收。
3. **我其实已经有边界，只是没总结成文**：在用 Claude Code 时心里大概有「能改 / 能跑 / 需确认」的判断，但没落成文字。这条正好接上挑战路径——把它们写成一份「我的 AI Coding 工作流 / 边界约定」。
