## 学习笔记（脚手架，请补自己的理解）

### 为什么要学这个
- 刚开始做 AI 应用，直接调一次模型 API 就够了；进入产品后会很快遇到：prompt 要版本管理、工具调用要有 schema、Agent 要记录 state、失败要重试、用户反馈要进评估、线上行为要能追踪。
- Frameworks 解决的是这些工程组织问题。它们不替你定义产品价值，也不保证模型输出正确，但可以帮你把复杂系统拆成更清楚的模块。
- 学框架最重要的判断不是「哪个最流行」，而是：**它到底帮你管理了哪一层复杂度，又把哪些复杂度藏起来了**。

### 第一性原理
- **框架是系统边界的表达，不是智能本身。先理解工作流，再决定用不用框架。**
- 很多失败的 AI 项目不是输在没有框架，而是先引入框架，再让产品逻辑迁就框架。更稳的方式：先画清楚输入、状态、工具、输出、评估和失败路径，再看哪些部分值得交给框架。
- 三条硬规则：
  - **简单链路先保持简单**：一次模型调用、一次检索、一次格式化输出，不一定需要复杂 Agent 框架。
  - **长流程需要显式状态**：多步任务、工具调用、人工确认、失败恢复，应该有可查询的 state，而不是只靠聊天历史。
  - **框架要能退出**：如果框架让你很难换模型、换向量库、换部署方式，长期成本会很高。

### 知识节点
- **LangChain**：最常见的 LLM 应用开发框架之一，覆盖模型接入、prompt、工具调用、retriever、agent、output parser 等模块。适合快速把模型能力和外部系统接起来，也适合学 AI 应用常见组件。但要小心「抽象太早」：还没搞清工作流就套一堆 chain 和 agent，后面排查会变难。LangChain 更像一套组件库，帮你组合能力，不替你决定产品边界。
- **LangGraph**：更偏向工作流和状态机，把 Agent 或多步任务表示成 graph：节点负责执行动作，边负责控制流，state 负责记录过程。任务只是「问一次答一次」时它太重；但多轮工具调用、重试、人工确认、分支、恢复和长期运行时，显式 graph 比一长串 prompt 历史更可靠。实用判断：**只要开始关心任务走到哪一步、能否恢复、失败后从哪里继续，就该考虑 graph / state machine**。
- **OpenAI Agents SDK**：用来构建带工具、handoff、guardrails、tracing 的 Agent 应用，价值是把 Agent 工作流里的常见工程问题做成可组合结构（Agent 的指令和工具 / 多 Agent handoff / 工具调用和结构化输出 / guardrails 和运行时追踪）。关键仍是边界：SDK 帮你执行流程，但你要定义哪些工具可用、哪些动作需要确认、什么输出算失败。
- **DSPy**：把 prompt / LM pipeline 写成可优化的程序。不是手工调一句 prompt，而是把输入输出、模块和指标定义清楚，再用 optimizer 改进 prompt 或调用策略。适合有明确数据集、评估指标和可重复任务（分类、抽取、问答、rerank、复杂推理链）。关键启发：**不要只靠感觉调 prompt，要让任务、数据和指标进入系统**。
- **Hermes**：更适合作为「面向工具调用和结构化输出的模型 / agent 生态」来理解，而不是通用框架。它提醒：框架不是唯一抽象层，模型本身是否擅长 tool calling、JSON mode、long context、reasoning 也影响系统设计。工具调用能力稳定的模型能减少解析和兜底成本。看这类方向不要只看榜单分数，要看它能否稳定产出你需要的结构化输出和工具调用格式。
- **Learning Agent**：指系统可以从反馈、日志、评估结果或用户修正中改进——不一定是训练模型，也可以是更新 prompt、调整 retriever、补充规则、改进测试集。真实产品里最容易踩的坑是**把线上反馈直接变成行为变化**，引入数据污染、越权学习和不可解释变化。更稳的流程：记录失败样本 → 人工/规则标注原因 → 加入 eval / regression set → 修改 prompt、检索、工具或模型配置 → 通过测试后再上线。**学习能力要先进评估闭环，再进入生产系统**。

### 在 AI x Web3 中的位置
Frameworks 在 AI x Web3 里负责把模型能力接到产品流程里：读取上下文、调用工具、生成结构化动作、记录 trace、进入 eval。但它不应该直接替代 Web3 侧的权限、签名、交易模拟和账户规则——框架可以组织 Agent，不能替用户承担资产风险。比较稳的分工是：**AI Framework 管理 prompt / tools / state / eval / trace；Web3 基础设施管理账户、签名、合约、交易和链上状态；产品层定义用户目标、权限边界、确认流程和失败处理。**

### 最小实践
做「文档问答 + 工具调用」的最小框架对比。同一任务两种实现：A 直接调模型 API（问题 + 检索结果 + JSON 输出）；B 用框架（同样输入输出 + tool schema + trace + 失败重试 + 测试样本）。对比四件事：哪个更易读、哪个更易加工具、哪个更易定位错误、哪个更易写回归测试。重点不是选冠军，而是看清框架到底帮了你什么。
